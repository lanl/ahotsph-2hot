# Welcome!

Thank your for taking the time to contribute. Please take a moment to read through these guidelines to make the process as frictionless as possible. 

This code is meant to stay useful both as production scientific software and as a somewhat gentle introduction to scientific and high-performance computing for newer contributors. This means that code changes should favor easy-to-read code, simpler/more explicit syntax, and documentation that errs on the side of being verbose. 

## Before you open a PR

- Read the local `README.md`, `INSTRUCTIONS`, and the relevant `Make-common/Make.<ARCH>` file before changing build logic.
- Prefer changes that improve correctness, maintainability, and clarity without making the code harder for new contributors to follow.
- Keep the number of added dependencies to a minimum. 
- Make sure your changes adhere to the code style guide as described below.
- Make sure that your PR includes unit tests, and, if appropriate, an example problem setup, that verifies the correctness of the added logic. This is a requirement even though this repo currently doesn't have unit test or a CI pipeline that automatically runs any tests. It soon will.

## What good contributions look like

- Keep patches focused. Separate unrelated fixes into separate PRs.
- Explain the scientific, numerical, or engineering reason for the change.
- Update nearby documentation or comments when behavior, assumptions, inputs, or outputs change.
- Add or update verification artifacts when practical: builds, smoke tests, control files, example usage, or reference outputs.
- Prefer clear and maintainable code over clever or overly modern code.
- Commit messages consist of a brief but descriptive title, followed by an empty line, followed by a 1-3 paragraphs long, concise description of the added change, followed by a trailer disclosing AI usage, if applicable, as described below.

## Verification expectations

- Build and verify from the repo you changed.
- For general tree changes, the standard build path is `make ARCH=<existing-arch> PAROS=[seq|mpi]` from `ahotsph-orig-tree16/`.
- New features should include passing tests, such as unit tests, focused build evidence, smoke tests, updated control files, documentation, or worked examples.
- As more automated checks are added to the project, contributors will be expected to keep them passing.

## Documentation expectations

- If a change affects behavior, workflows, build steps, assumptions, inputs, outputs, or limitations, update the relevant documentation, comments, control files, or examples.
- User-visible or workflow-visible changes should usually update at least one of: `README.md`, `INSTRUCTIONS`, nearby source comments, or checked-in example inputs.
- When a design tradeoff is not obvious to non-experts, especially around numerical behavior, performance, or portability, leave enough explanation for the next contributor to understand why the code looks the way it does. 

## Style and code quality

- Follow the existing local code style and use `.clang-format` as the style reference where it applies.
- Do not hand-edit generated `DO NOT DELETE` dependency blocks in makefiles unless the task is specifically about dependency generation.
- If machine-specific compiler or linker flags need to change, update the relevant `Make-common/Make.<ARCH>` file instead of patching leaf makefiles.
- Avoid unnecessary boilerplate, dead code, and large rewrites without a strong reason.

## AI tool usage and disclosure

You may use AI tools to assist your contributions. You remain fully responsible for everything you submit.

- You must be able to explain the change and review it line by line if asked.
- AI tools must not be used to fix issues labeled `good first issue`; those are reserved for human learning.
- Do not open PRs that expect the maintainer to finish, debug, or validate AI-generated logic for you.

### Commit trailers

Use the following disclosure levels for commits:

- Level 0: Human

  The change (code, docs, commit) was largely/fully generated by the human committer. This includes the use of agents for line completion, boilerplate generation, regex construction, renaming variables, debugging errors, and similar light tasks. No trailer is required for this.

- Level 1: Agent assisted

  A human collaboratively used an AI agent to develop, design, and/or implement the logic, write unit/etc. tests, write documentation, write commit or PR messages, and **verified** everything that was produced by the AI. Also known as the responsible use of AI. Use the trailer `Assisted-by: <agent> (<llm-model>-<llm-version>)`

  Example:

  ```text
  Fix memory leak in buffer allocation

  Assisted-by: Claude (anthropic/claude-3.7-sonnet)
  ```

- Level 2: AI generated

    A human prompts an AI agent (e.g., Devin, Sweep, or an automated pipeline) with an entire GitHub issue or large task, and the bot autonomously generates the branch, writes the code, and opens the PR. No, or no thorough, review of the produced changes by a human was done. This also includes "vibe-coding". `Generated-by: <tool> (<llm-model>-<llm-version>) [, <tool> (<llm-model>-<llm-version>) ...]` 
  
  Example:

  ```text
  Fix memory leak in buffer allocation

  Generated-by: Codex (GPT-5.6-Sol)
  ```

## Maintainer review expectations

- PRs should be small enough to review safely.
- Large, difficult-to-verify, or poorly explained changes may be asked to split or may be declined.
- Contributors are expected to own the correctness, documentation, and maintainability of what they submit.

Thanks for helping keep this codebase useful, readable, and scientifically trustworthy.
